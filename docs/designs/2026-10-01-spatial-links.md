# SPEC — Elsewhere: Spatial Link Mechanic

> **Prototype status (1 October 2026):** implemented as the micro-level **The Fold** (`monuments/the_fold.tscn`, generated by `tools/gen_fold.py`) on branch `feature/spatial-links`. Not part of the main game and not used by The Ring. See [Prototype implementation](#prototype-implementation-the-fold) at the end.

## 0. Status

**Feature:** Spatial Links / Architectural Gates  
**Project:** *Elsewhere*  
**Status:** Experimental mechanic — prototype before integration into the main game  
**Purpose:** Give first-person gameplay a distinctive active mechanic that complements isometric architectural manipulation.

The mechanic takes inspiration from portal-based spatial connections, but should **not** become a free-placement portal gun.

The intended identity is:

> **First person decides what spaces are connected.  
> Isometric view decides where those connected spaces are.**

---

# 1. Design Goal

First person already has an informational role in *Elsewhere*:

- discovering interiors;
- understanding top vs underside;
- finding sightlines;
- experiencing scale;
- learning spatial relationships hidden from the authored isometric composition.

Spatial Links add an **active puzzle verb** to first person.

Instead of only discovering the monument, the player can modify its local topology by linking authored architectural thresholds.

The mechanic should strengthen the existing core question:

> **Where do I need to be before I change the space?**

with a second question:

> **Which spaces should I connect before I change the space?**

---

# 2. Core Concept

Certain architectural openings are **Linkable Thresholds**.

Examples:

- doorframes;
- arches;
- recessed openings;
- passage mouths;
- geometric apertures.

The player can create a spatial connection between two compatible thresholds.

Once linked:

> entering Threshold A exits through Threshold B.

The connection is bidirectional unless a specific future puzzle explicitly introduces another established rule.

The linked spaces do not need to be physically adjacent.

---

# 3. What This Is Not

The player does **not**:

- shoot portals onto arbitrary surfaces;
- place gateways freely;
- create portals on every wall;
- bypass authored traversal;
- use a portal gun;
- solve puzzles primarily through physics momentum.

The mechanic should remain part of the architecture rather than becoming a universal traversal tool.

This distinction protects *Elsewhere* from becoming:

> “Portal plus rotating buildings.”

---

# 4. Perspective Roles

## First Person

First person is responsible for:

> **Explore → Discover → Connect**

The player:

- physically reaches thresholds;
- investigates where they lead;
- discovers hidden candidate links;
- creates or changes Spatial Links;
- traverses those links.

## Isometric

Isometric view is responsible for:

> **Understand → Transform**

The player:

- reads the overall monument;
- sees major structural relationships;
- selects transformable architecture;
- rotates or reconfigures structures.

Spatial Link creation itself should remain a first-person action.

---

# 5. Linkable Thresholds

Each valid gateway is authored into the level.

A threshold contains:

```text
SpatialThreshold
- ID
- Transform
- Ground reference
- Entry direction
- Exit direction
- Link group / compatibility
- Current linked threshold
- Discovered state
- Active state
```

A threshold is part of the architectural monument rather than an abstract gameplay marker.

---

# 6. Discovering Thresholds

Not every threshold needs to be available immediately.

Possible states:

```text
Hidden
Discovered
Available
Linked
Unavailable
```

A threshold might only become known after:

- physically reaching it;
- seeing it from first person;
- entering a hidden interior;
- activating a local architectural element.

This supports the current *Elsewhere* principle:

> **First person discovers information.**

---

# 7. Creating a Link

Baseline interaction:

1. Reach a linkable threshold in first person.
2. Interact with it.
3. The threshold becomes the current link source.
4. Reach or target another compatible discovered threshold.
5. Activate it.
6. The two thresholds become spatially connected.

Exact input and presentation remain to be prototyped.

The interaction should feel architectural rather than weapon-based.

Possible presentation:

- touch the frame;
- activate an embedded symbol;
- trace a short line of light;
- briefly illuminate both thresholds;
- architectural seams respond.

---

# 8. Link Capacity

### Prototype rule

The player may maintain **one active threshold pair at a time**.

This gives:

```text
A ↔ B
```

Activating:

```text
C ↔ D
```

removes the previous link.

This keeps the system readable and prevents combinatorial explosion during initial testing.

Multiple simultaneous links can be explored later if puzzle design proves it necessary.

---

# 9. Traversal Through a Link

Crossing should feel like walking through ordinary architecture.

The player should not stop, fade out, or explicitly teleport if the implementation can support seamless traversal.

The transition preserves:

- movement continuity;
- player-relative position within the aperture;
- appropriate heading;
- current velocity where relevant.

The destination threshold defines the new local ground relationship.

---

# 10. Gravity Through Spatial Links

This is one of the primary opportunities to make the system feel specific to *Elsewhere*.

The baseline rule should be:

> **The player adopts the destination threshold's ground orientation.**

Example:

Threshold A is on a conventional floor.

Threshold B is attached to what appears from world space to be a wall.

The player walks through A and emerges through B already oriented so B's associated surface is their ground.

This combines:

> **spatial connection + gravity reorientation**

into one coherent traversal rule.

---

# 11. Orientation Mapping

A threshold must define a complete traversal frame:

```text
up      = destination ground normal
forward = direction leaving the threshold
right   = up × forward
```

Player position and motion are transformed from the source frame into the destination frame.

This allows two thresholds to be linked even when they have completely different world orientations.

---

# 12. Links on Moving Architecture

Spatial thresholds belong to their structures.

If a linked threshold is attached to a rotating structure:

> **the threshold moves with that structure and the link remains active.**

This is essential to combining the mechanic with the existing game.

Example:

```text
Threshold A → fixed tower
Threshold B → rotating ring
```

The player creates:

```text
A ↔ B
```

Then rotates the ring in isometric view.

Threshold B moves with it.

The connection remains:

```text
A ↔ B
```

but B now exists in a different architectural configuration.

This creates a new class of puzzle.

---

# 13. Core Combined Loop

A Spatial Link puzzle can use:

```text
Explore in first person
        ↓
Discover thresholds
        ↓
Choose a connection
        ↓
Traverse / reposition
        ↓
Open isometric view
        ↓
Transform architecture
        ↓
The linked threshold moves
        ↓
Return to first person
        ↓
Use the changed connection
```

This makes first-person actions and isometric transformations interdependent.

---

# 14. Core Puzzle Question

A successful puzzle should require reasoning about both:

```text
Player position
+
Spatial Link state
+
Architectural configuration
```

Conceptually:

```text
Puzzle State =
Player location
+ Player supporting surface
+ Structure configurations
+ Active path connections
+ Spatial Link pair
```

---

# 15. Example Puzzle

A monument contains three thresholds:

```text
A — Entry
B — Rotating structure
C — Goal side
```

Initial state:

- A is accessible.
- B is attached to a rotating frame.
- C is inaccessible.

The player creates:

```text
A ↔ B
```

and crosses to the frame.

They then enter isometric view and rotate the structure carrying B.

B now faces a different part of the monument.

The player returns to first person.

From this new position, they discover C.

They replace the connection:

```text
B ↔ C
```

and use it to continue.

A deeper version could require the player to occupy the correct side of B **before** rotating the structure.

---

# 16. Desired Puzzle Relationships

Spatial Links should support situations such as:

### Prepare Before Moving

Create a connection before rotating a structure because the source threshold becomes inaccessible afterward.

### Carry a Connection

Move a linked threshold through space by rotating the architecture it belongs to.

### Change Orientation

Use a threshold to access a destination surface with a different gravity frame.

### Reuse a Threshold

A gateway initially acts as an entrance and later becomes an exit to a different location.

### Position Dependency

The correct link exists, but the player is on the wrong side of the transformable structure.

### Link Conflict

Choosing one connection means another useful connection cannot exist simultaneously.

---

# 17. What Should Not Create Difficulty

Avoid puzzles based primarily on:

- guessing which random pair of frames works;
- trying every possible combination;
- portals hidden with no clue;
- extremely precise first-person aiming;
- arbitrary link compatibility;
- unclear orientation after traversal.

The player should be able to form a hypothesis.

Desired loop:

> **Observe → infer → link → test → understand the consequence.**

---

# 18. Visual Language

Spatial Links should not look like conventional glowing oval portals.

The architecture itself should remain dominant.

Potential appearance:

- the interior of a doorway subtly shows the destination;
- a thin emissive seam runs around the linked frame;
- the opening has slightly altered depth/parallax;
- both linked thresholds share a restrained accent;
- the destination appears spatially continuous through the opening.

The effect should feel like:

> **two pieces of architecture have become adjacent**

rather than:

> **a magical portal was pasted onto the wall.**

---

# 19. Naming Direction

Avoid presenting the mechanic primarily as “portals.”

Possible internal or player-facing terms:

### Spatial Link
Clear and functional.

### Stitch
Implies stitching two places together.

### Fold
Suggests folding space.

### Threshold
Focuses on the architecture.

### Link
Minimal and readable.

### Elsewhere
Potentially thematic:

> a threshold leading elsewhere.

**Working technical name:** `SpatialLink`

Final player-facing terminology remains TBD.

---

# 20. First-Person Interaction

The mechanic should not require a gun.

Possible interaction model:

```text
Look at Threshold A
→ Interact
→ A becomes primed

Look at / reach Threshold B
→ Interact
→ A ↔ B created
```

Visual feedback should clearly communicate:

- selected source;
- valid destination;
- active pair.

The system should require very little permanent HUD.

---

# 21. Isometric Representation

The isometric view should show that thresholds exist without exposing all first-person information.

A discovered active link may use a subtle indicator.

Examples:

- matching edge illumination;
- small architectural glyph;
- restrained connection state highlight.

Do **not** draw a giant line through the level connecting the two thresholds unless testing proves necessary.

The player should reason primarily from the monument itself.

---

# 22. Relationship With Authored Isometric Camera

Free orbit remains removed.

This is especially important with Spatial Links.

Otherwise the player could use the isometric camera as a 3D inspection tool to search for hidden thresholds.

The intended division remains:

> **First person discovers.  
> Isometric reasons and transforms.**

---

# 23. Relationship With Existing Movement

Spatial Links must work with:

- authored walkable paths;
- gravity curves;
- moving supports;
- surface-relative movement;
- carried player poses.

They should **extend** traversal rather than replace it.

A level should not become:

> portal → portal → portal → goal.

Gravity paths, architectural exploration and positioning remain important.

---

# 24. Relationship With The Ring

Do **not** immediately retrofit Spatial Links into Ring v3.

Ring v3 is currently valuable because it tests:

- hidden first-person information;
- side changing;
- two rotors;
- top vs underside;
- player positioning.

Adding another mechanic would contaminate that test.

The first Spatial Link prototype should be a separate micro-level.

---

# 25. Prototype Level

Build the smallest possible test.

### Geometry

- one fixed room / monument;
- three Spatial Thresholds;
- one rotatable architectural piece;
- two ground orientations;
- one destination.

### Required systems

```text
Threshold A
Threshold B
Threshold C
RotatableStructure
PlayerStart

```

No final art.

---

# 26. Prototype Questions

The prototype exists to answer:

### Question 1

Is creating links in first person satisfying by itself?

### Question 2

Does moving a linked threshold through isometric transformation create interesting reasoning?

### Question 3

Does changing gravity through a threshold feel natural?

### Question 4

Does the mechanic strengthen first-person identity without replacing the existing positioning system?

### Question 5

Can players understand why a connection changed after transforming its structure?

---

# 27. Prototype Success Condition

A successful test should create a realization similar to:

> “I need to connect these two places now, move myself onto that structure, rotate it, and then use the same connection from its new orientation.”

The player should not merely think:

> “I found the portal that takes me to the exit.”

---

# 28. Prototype Failure Conditions

Do not integrate the mechanic if testing shows that:

- free linking trivializes architectural traversal;
- every puzzle becomes a portal puzzle;
- the isometric transformations become secondary;
- players solve by brute-forcing threshold combinations;
- gravity transitions through links are confusing;
- the mechanic feels too directly derivative of *Portal*;
- the additional system creates complexity without producing better deductions.

---

# 29. Scope Restrictions

For the first prototype:

- one active pair;
- no momentum puzzles;
- no physics-object portals;
- no arbitrary surface placement;
- no moving projectiles through links;
- no recursive portal views;
- no multiple nested links;
- no player-created geometry;
- no portal combat.

Keep the test focused on:

> **space + position + transformation.**

---

# 30. Technical Model

Conceptually:

```text
SpatialLinkManager
 ├── SourceThreshold
 ├── DestinationThreshold
 └── ActiveLink
```

Threshold:

```text
SpatialThreshold
 ├── Transform
 ├── OwningStructure
 ├── GroundFrame
 ├── LinkGroup
 ├── Discovered
 ├── Enabled
 └── LinkedThreshold
```

On traversal:

```text
source local player pose
        ↓
convert into source threshold frame
        ↓
map into destination threshold frame
        ↓
apply destination support / gravity frame
        ↓
continue movement
```

---

# 31. Save State

If integrated into the main game, puzzle snapshots should include:

```text
active_link_source
active_link_destination
discovered_thresholds
```

Undo may also need to restore link state if linking is considered part of puzzle manipulation.

Whether first-person linking itself participates in the main Undo stack remains **TBD**.

---

# 32. Interaction With Moving Structures

If a threshold belongs to a transformable piece:

```text
Threshold local transform
    remains fixed relative to structure

Structure transforms
    ↓
Threshold transforms

Spatial Link
    remains active
```

Player traversal must use the threshold's **current world transform**, not the transform from when the link was created.

---

# 33. Debugging Requirements

Prototype debug display should be able to show:

- threshold IDs;
- current compatible pair;
- active link;
- source/destination frames;
- ground normals;
- owning structures.

Useful debug mode:

```text
F3:
A ↔ B
A owner: FixedTower
B owner: RotatingFrame
B ground: +X
```

This should not exist in final presentation.

---

# 34. Tests

Minimum automated coverage:

### Link creation

Valid compatible thresholds link successfully.

### Replacement

Creating a new pair replaces the old pair.

### Bidirectionality

A → B and B → A both work.

### Pose mapping

Relative entry position maps correctly to the destination aperture.

### Ground mapping

Player exits using destination ground orientation.

### Moving threshold

A linked threshold attached to a rotated structure uses its updated transform.

### Save / Reload

Active link state restores correctly.

### Invalid pairing

Incompatible thresholds cannot link.

### Player support

Traversal leaves the player assigned to the correct destination support/path.

---

# 35. Human Playtest Questions

After the prototype, ask:

- Did you understand what linking two thresholds would do before trying it?
- Did you understand that the linked doorway moved with the structure?
- Did you feel in control of your orientation after crossing?
- Did you think about where to stand before transforming the structure?
- Did the mechanic feel like part of the architecture?
- Did it immediately remind you too strongly of *Portal*?
- Did linking spaces make the puzzle more interesting, or only more complicated?

---

# 36. Integration Rule

Spatial Links only enter the main *Elsewhere* design if they satisfy this principle:

> **They must deepen the relationship between first-person position and isometric transformation.**

They should not simply add another traversal shortcut.

---

# 37. Updated Perspective Identity

If validated:

## First Person

> **Discover, traverse, and connect space.**

## Isometric

> **Understand and transform architecture.**

Together:

> **Connect locally. Transform globally.**

---

# 38. Core Mechanic Statement

The strongest version of the feature is:

> **The player links authored architectural thresholds in first person. Those thresholds remain attached to the structures that contain them, so transforming the architecture in isometric view also transforms the spatial relationships the player created.**

This is the concept worth prototyping.

---

# 39. One-Sentence Rule

> **First person chooses what is connected; isometric view changes where those connections exist.**

# Prototype implementation (The Fold)

## Decisions taken for the prototype

- **No destination rendering.** A linked doorway shows a shared seam, not the place it leads to. Crossing is an instant, pose-continuous cut. True destination rendering is the next, separately controlled experiment (an A/B comparison on the same puzzle).
- **Linking: one step, nothing hidden (revised after the first playtest, where linking itself felt unintuitive).**
  - Standing at a doorway makes it the **source**: its seam glows warm, a soft veil fills it, and every compatible doorway in sight is highlighted as a candidate. A reticle appears.
  - Looking at a doorway **aims** at it. Aiming is generous (14°) and held against drift (22°), so the difficulty is choosing a doorway, not hitting one. A **tether** previews the link from source to target, and the prompt reads **"F  Link A ↔ B"** (or says why not, e.g. "B does not fit A").
  - **F** links: the tether flares, both doorways take the link colour, and the old pair goes dark.
  - **Visibility is the only rule:** a compatible doorway in sight can be linked; no earlier discovery is needed.
  - **Doorways behind doorways (second playtest).** Aiming follows the view ray first. A doorway's frame selects it; its opening is looked *through*, so a linkable doorway beyond it is meant instead. With no ray hit, the generous cone applies.
- **One pair (§8).** A new link replaces the old one.
- **Undo (§31).** The link is puzzle configuration: undo, restart, checkpoints and saves restore it. **Discovery is knowledge**: undo and restart never make the player forget a doorway; saves keep it; only a fresh save resets it. (Restart keeping discovery is a one-line choice to revisit after playtesting.)
- **Discovery (§6)** now only decides what the overview shows. A doorway is noticed when at least 2 of 4 aperture points (centre, left, right, top) are in view, within the level's `discovery_range` and in clear line of sight for **0.25 s**. A doorway's own frame and deck never hide it. The isometric view never discovers anything, and undiscovered doorways show no seam there (§21–22).
- **Gravity (§10–11).** Crossing maps the pose through `frame(B) · half-turn · frame(A)⁻¹`: a rotation, never a reflection, so player-left stays left. The player arrives walking into B's path on B's ground, 5 cm inside, so a held key crosses exactly once.
- **Moving thresholds (§12, §32).** Links are read from current transforms at crossing time. The isometric composition turns with the crossing.
- **Prototype art.** `blockout_frame` adds jambs and a lintel; custom architecture can replace them. The seam (hidden, dim, primed, linked) is the behaviour's feedback.

## Link study

`monuments/link_study.tscn` (`tools/gen_link_study.py`) tests the interaction on its own: three doorways in one open space, nothing to turn, no puzzle. A stands at the edge of the plaza; B faces it across a gap (with the light); C faces it from a higher platform. **Play this first.** If standing at A, looking at B and pressing F is not immediately understandable and satisfying, stop polishing the UI: the remote pairing itself may be too abstract, and a more embodied verb (drawing or stitching the connection) is the next idea to test. Only if it works does The Fold test the puzzle.

## The Fold

| Piece | Role |
|---|---|
| **Entry** (fixed, upright) | Start. Doorway **A** at its edge, facing the frame |
| **Frame** (turns about X, 4 states) | Its inner deck carries doorway **B**. State 0: the deck is a floor and the frame's west window shows B from the entry. State 1: the deck is a wall |
| **Screen** (fixed) | A slot that lines up with the frame deck only in state 1 |
| **Goal wall** (fixed, sideways ground) | Doorway **C** and the goal |

**Legibility (second playtest: start and end looked alike).**
- **Distinct places:** a warm lantern marks the entry, and the goal is a broad terrace under a light shaft.
- **Named doorways:** each has a sign above its lintel (disc A, diamond B, bars C).
- **The frame's floor:** accent edges mark its deck side, so the deck reads as a floor even when it is a wall.
- **Something to face on arrival:** a warm rim frames the west window, so arriving on the deck you face a lit opening with A's sign beyond it.

No ordinary path joins any two pieces. Intended solution: link **A↔B** while B is in sight → turn the frame once → walk through A, arriving on the deck that is now a wall → look back out through B and the slot to discover **C** → link **B↔C** (the way back is gone) → walk through B to the goal.

Tests (`tests/link_tests.gd`) pin the sight lines in every frame state, play the solution through the runtime, check the turn-first dead end, and solve the level over authored positions: minimum **2 links, 1 turn, 2 crossings**, unsolvable without links or without turning.

## Playtest script

Play from a fresh save without hints first. Then ask (spec §35):

- Did you understand what linking two thresholds would do before trying it?
- Did you understand that the linked doorway moved with the structure?
- **At what moment did you realise the doorway itself had moved, rather than the link having changed?**
- Did you feel in control of your orientation after crossing?
- Did you think about where to stand before transforming the structure?
- Did the mechanic feel like part of the architecture?
- Did it immediately remind you too strongly of *Portal*?
- Did linking spaces make the puzzle more interesting, or only more complicated?

The integration gate is §28 and §36. Success is the realisation of §27, not reaching the goal.

## Next prototype, if The Fold succeeds

The Fold is deliberately artificial (no physical routes), so it cannot answer the real integration question: **do links deepen Elsewhere's architecture, or replace it?** The next test combines ordinary traversal, a gravity curve, one link and one transformable structure. Only after that, the A/B test with destination rendering.
